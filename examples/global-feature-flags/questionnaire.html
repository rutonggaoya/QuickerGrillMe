Goals and service boundary · high impact

What should the data plane optimize for when the control plane or network is unavailable?

  • Availability first with bounded stalenessSelectedRecommended

    Continue evaluating from the last verified snapshot and expose its age.

  • Consistency first

    Reject evaluation when fresh configuration cannot be confirmed.

  • Per-flag failure policy

    Let each flag choose stale, default-off, or error behavior.

Agent recommendation: Feature evaluation commonly sits on critical request paths, so a verified stale snapshot is safer than turning a control-plane incident into a global application outage.

Data plane · high impact

Where should production flag evaluation run?

  • In-process SDKSelectedRecommended

    Applications evaluate locally from signed, versioned configuration snapshots.

  • Sidecar or node-local daemon

    A local service centralizes evaluation and snapshot distribution per host or cluster.

  • Remote evaluation API

    Applications call a regional service for each evaluation.

Agent recommendation: Local evaluation removes a network hop from hot paths and preserves availability during regional control-plane failures.

Consistency · high impact

What propagation guarantee should operators receive after publishing a flag change?

  • Bounded eventual consistency

    Publish a target propagation SLO and show per-region convergence status.

  • Globally ordered activation

    Do not acknowledge publication until all required regions can observe one committed version.

  • Tiered consistencySelectedRecommended

    Use bounded eventual consistency normally and stronger coordination for emergency flags.

Agent recommendation: Most flags benefit from fast regional propagation, while kill switches justify a narrower, stronger operational path.

Privacy and targeting · high impact

How much user or tenant data may enter the evaluation engine?

  • Typed context evaluated locallySelectedRecommended

    SDKs evaluate approved attributes in process and do not send raw context to the platform.

  • Pseudonymous identifiers only

    Allow stable hashed IDs for percentage rollout and cohort membership.

  • Centralized context service

    Upload targeting attributes to support server-side evaluation and analysis.

Agent recommendation: Keeping evaluation context inside the application minimizes privacy exposure and removes a global user-profile dependency.

Distribution · high impact

How should configuration reach globally distributed SDKs?

  • Regional streams with polling fallbackSelectedRecommended

    Regional relays push version notifications; SDKs fetch snapshots and poll when streams fail.

  • CDN snapshot polling

    SDKs periodically fetch immutable snapshots from a global CDN.

  • Direct global streaming

    Every SDK maintains a stream to the central control plane.

Agent recommendation: Regional fan-out gives fast propagation without making persistent global connectivity the only recovery path.

Distribution · high impact

What must an SDK verify before activating a new configuration snapshot?

  • Control-plane signatureSelectedRecommended

    Verify provenance and reject forged or corrupted snapshots.

  • Monotonic versionSelectedRecommended

    Reject accidental rollback unless explicitly authorized.

  • Schema and semantic validationSelectedRecommended

    Reject malformed rules, missing defaults, and incompatible evaluator versions.

  • Transport checksum only

    Rely on TLS and content checksums without a signed artifact.

Agent recommendation: A bad global snapshot can affect every request path, so activation must be atomic and independently verifiable.

Control plane · high impact

How should flag writes work across regions?

  • Single writer with regional failoverSelectedRecommended

    Route writes to one home region and promote a standby through a controlled failover.

  • Multi-region consensus

    Accept writes in several regions through one globally ordered log.

  • Project ownership by region

    Assign each project a write region while replicating reads globally.

Agent recommendation: Configuration writes are low volume; a single ordered authority simplifies auditability, versioning, and conflict handling without affecting local evaluation.

Release safety · high impact

Which safeguards should be mandatory for high-impact flag changes?

  • Progressive rollout stagesSelectedRecommended

    Increase exposure through explicit, observable stages.

  • Metric-triggered rollbackSelectedRecommended

    Revert when linked guardrail metrics breach thresholds.

  • Second-person approvalSelectedRecommended

    Require review for production or emergency-class changes.

  • Change windows

    Restrict high-impact changes to staffed operating windows.

Agent recommendation: A global control surface needs both blast-radius reduction and a fast automated escape path; approval protects against operator error.

SDK compatibility · high impact

How should rule semantics evolve across many SDK languages?

  • Versioned rule IR with conformance suiteSelectedRecommended

    Publish a language-neutral evaluator contract and certify SDKs against shared vectors.

  • Server-compiled lookup tables

    Compile rules centrally into simpler runtime-specific artifacts.

  • Independent SDK implementations

    Document behavior and let each language evolve separately.

Agent recommendation: Local evaluation is only trustworthy when identical context produces identical results across supported runtimes.

Observability and privacy · medium impact

What evaluation telemetry should the platform collect by default?

  • Sampled aggregate countersSelectedRecommended

    Report flag/version/result counts without raw targeting context.

  • Per-evaluation events

    Emit detailed decision events for debugging and experimentation.

  • Operational health only

    Collect snapshot age, errors, and SDK health but no evaluation results.

Agent recommendation: Aggregates support rollout health and adoption analysis while limiting cost, cardinality, and privacy exposure.

Operations · medium impact

How strongly should the platform enforce flag cleanup?

  • Owner and expiry requiredSelectedRecommended

    Every temporary flag has an owner, expiry, reminders, and escalation.

  • Advisory lifecycle metadata

    Recommend ownership and expiry without blocking creation.

  • External governance

    Leave cleanup policy to service teams and inventory tooling.

Agent recommendation: Stale flags compound evaluator complexity and operational ambiguity; lifecycle metadata is cheapest to capture at creation.

Failure recovery · high impact

What recovery path should exist for a bad global configuration or control-plane loss?

  • Immutable version historySelectedRecommended

    Retain every published snapshot and its audit record.

  • Explicit signed rollbackSelectedRecommended

    Authorize SDKs to activate a prior version through a new monotonic command.

  • Offline emergency bundle

    Distribute a separately controlled minimal kill-switch artifact.

  • Application defaults onlySelectedRecommended

    Rely on compiled defaults when no valid platform snapshot is usable.

Agent recommendation: Recovery needs an auditable rollback that does not weaken monotonic version checks, plus application-owned defaults for total platform loss.

Product boundary · medium impact

Should experimentation analytics be part of the initial platform boundary?

  • Separate experimentation integrationSelectedRecommended

    Expose stable assignments and events to a dedicated analytics system.

  • Built-in experimentation

    Own assignment, exposure logging, metric computation, and statistical analysis.

  • No experimentation contract

    Limit the platform to operational feature delivery.

Agent recommendation: Flag delivery and statistical analysis have different data, privacy, and correctness concerns; a stable integration avoids coupling their release paths.
